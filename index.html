01

C# foundations

Unity scripting is C#. Learn the language building blocks first; the same skills apply whether you write a tiny behaviour or a large gameplay system.

Values, variables & types

A variable names a value. C# is statically typed: the compiler checks that you use compatible types.

C# · values
int health = 100;
float moveSpeed = 4.5f;
bool isGrounded = false;
string playerName = "Rook";

health -= 10;                 // health is now 90
Debug.Log($"{playerName}: {health}");

Use int for whole numbers, float for common Unity decimals (with the f suffix), and bool for true/false.

Decisions & loops

Branches choose behavior; loops repeat it. Prefer clear, bounded loops over work that can run forever.

C# · control flow
if (health <= 0)
{
    Debug.Log("Out of health");
}

for (int i = 0; i < 3; i++)
{
    Debug.Log($"Wave {i + 1}");
}

Methods & parameters

Methods package work behind a name. Parameters are inputs; a return value is the output.

C# · method
float GetDamage(float baseDamage, float multiplier)
{
    return baseDamage * multiplier;
}

float hit = GetDamage(12f, 1.5f); // 18

Classes, objects & encapsulation

A class describes a kind of object. Fields store state; methods define behavior. Keep implementation details private and expose deliberate operations.

C# · object design
public class HealthPool
{
    public int Current { get; private set; }

    public HealthPool(int startingHealth)
    {
        Current = startingHealth;
    }

    public void TakeDamage(int amount)
    {
        Current = Math.Max(0, Current - amount);
    }
}

Collections, enums & null

Use arrays for fixed-size sequences, List<T> for growable lists, and dictionaries for key/value lookup. Enums name a limited set of states. Check references that may be null before using them.

C# · collections
enum DoorState { Locked, Closed, Open }
List<string> inventory = new();
inventory.Add("Key");

if (inventory.Count > 0)
    Debug.Log(inventory[0]);

Interfaces, inheritance & composition

Inheritance says “is a”; interfaces say “can do”. Prefer small components cooperating over deep inheritance trees.

C# · contract
public interface IDamageable
{
    void TakeDamage(int amount);
}

public class Crate : MonoBehaviour, IDamageable
{
    public void TakeDamage(int amount) { /* ... */ }
}

02

Unity & components

Unity turns C# scripts into scene behaviors through GameObjects, Components, assets, and lifecycle callbacks.

Project, scene, GameObject

A project is the workspace and asset database. A scene is a saved arrangement of objects. A GameObject is a container; its Components give it data and behavior.

  • Transform is the basic position, rotation, and scale component.
  • Scripts, colliders, cameras, and renderers are components too.
  • Assets are project files; instances in a scene are not the same thing as their source asset.

Your first MonoBehaviour

Attach a MonoBehaviour script to a GameObject to let Unity call its event methods.

PlayerMover.cs
using UnityEngine;

public class PlayerMover : MonoBehaviour
{
    [SerializeField] private float speed = 5f;

    void Update()
    {
        float x = Input.GetAxis("Horizontal");
        transform.Translate(Vector3.right * x * speed * Time.deltaTime);
    }
}

In a project, the public class name should match the script filename. Serialized private fields are editable in the Inspector without making them public.

Inspector, references & prefabs

The Inspector edits serialized component data. Drag references into fields, or find them deliberately at runtime. Prefabs are reusable object templates with overrides and nested composition.

Reference safely
[SerializeField] private Transform target;

void Start()
{
    if (target == null)
        Debug.LogError("Assign a target in the Inspector", this);
}

Lifecycle, in a useful order

Awake initializes this object; OnEnable subscribes/activates; Start runs before its first frame; Update runs per rendered frame; OnDisable/OnDestroy clean up.

Don't assume every object's Awake order. Use explicit initialization or Script Execution Order only when ordering is truly required.

03

Gameplay scripting

Connect input, time, physics, animation, UI, and data into maintainable game behavior.

Input & frame time

For new projects, Unity's Input System package provides action maps, rebinding, and device abstractions. Poll or subscribe to actions deliberately. Scale frame-based movement with delta time.

Simple movement
void Update()
{
    Vector2 move = moveAction.ReadValue<Vector2>();
    Vector3 direction = new(move.x, 0f, move.y);
    transform.position += direction * speed * Time.deltaTime;
}

Physics & collision

Use a Rigidbody for physics-driven motion and colliders for contact. Apply forces in FixedUpdate when continuously simulating; collision callbacks report contacts. Avoid moving a dynamic Rigidbody by directly changing its Transform.

Physics callback
void FixedUpdate()
{
    body.AddForce(moveDirection * acceleration);
}

void OnCollisionEnter(Collision hit)
{
    Debug.Log($"Hit {hit.gameObject.name}");
}

Coroutines & async work

A coroutine pauses and resumes on Unity's main thread. It is useful for sequences and delays, not parallel CPU work. Use cancellation and lifecycle cleanup; use async APIs for supported asynchronous operations.

Wait, then act
IEnumerator FlashAfterDelay(float seconds)
{
    yield return new WaitForSeconds(seconds);
    renderer.enabled = !renderer.enabled;
}

Animation & UI

Drive Animator parameters from gameplay state instead of hard-coding animation timing. Use UI Toolkit or uGUI consistently for the project's needs; update visible UI when data changes rather than searching the scene every frame.

Events & ScriptableObjects

Events decouple a sender from listeners, but always unsubscribe. ScriptableObjects are project assets suited to shared configuration and authored data—not a magic replacement for runtime save data.

Simple event subscription
void OnEnable()  => health.Damaged += OnDamaged;
void OnDisable() => health.Damaged -= OnDamaged;

Architecture that stays understandable

Give each component a clear responsibility. Inject references, validate assumptions, separate game rules from presentation, and profile before optimizing. Patterns such as state machines and object pools solve specific problems; they are not requirements for every project.

04

Inside the Unity Editor

The Editor is an application for authoring and running projects—not simply a visual front end. Its architecture combines native engine/editor code with managed C# tooling and an extensible package ecosystem.

A useful mental model

Native coreEngine, platform, rendering and editor services (largely C++)
Managed layerC# runtime APIs and editor-facing managed code
PackagesOptional tools and features with versioned APIs
Editor UIWindows, inspectors, importers and custom tools

Exact implementation varies by subsystem and Unity version. The Editor is not a single C# program: native subsystems provide core engine functionality, while managed code exposes APIs and supports many extensibility workflows. UI Toolkit and IMGUI are UI technologies, not the whole Editor implementation.

What happens when scripts compile?

Unity imports assets, compiles assemblies, refreshes editor state, and reloads managed code when needed. Assembly Definition assets (.asmdef) partition code into assemblies, can reduce recompilation scope, and express references. Enter Play Mode may reload domain and scene state depending on settings.

Custom Editor tooling

Editor-only code belongs in an Editor folder or editor-only assembly. Custom inspectors and windows use Editor APIs, such as UI Toolkit or IMGUI. Keep editor references out of player builds.

Editor-only guard example
#if UNITY_EDITOR
using UnityEditor;
#endif

// Prefer keeping editor scripts in an Editor-only assembly.

Import pipeline & asset database

When files change, importers convert source assets into engine-ready data and maintain references/dependencies. Meta files carry stable asset identity; version-control them alongside assets. Avoid casually editing generated Library data.

Play Mode is a simulation workflow

The Editor enters Play Mode by initializing runtime systems and loading scene state. It can differ from a built player in timing, platform APIs, graphics, and asset inclusion. Test in player builds too.

06

ML-Agents & game AI

Unity ML-Agents connects a Unity environment to reinforcement-learning and imitation-learning workflows. It is a training toolkit—not an automatic “make smart enemies” button.

Agent, observations, actions, rewards

An Agent gathers observations, requests an action, applies that action to the environment, then receives reward and episode signals. Training runs through a trainer configuration; a trained policy is later used for inference.

Design the learning problem

  • Observations should contain enough information to choose an action.
  • Action spaces should be as small as the task allows.
  • Rewards should align with the real goal; sparse rewards can make learning difficult.
  • Reset episodes consistently, and avoid leaking answers into observations.

Typical workflow

Install a compatible ML-Agents package/toolchain version, create a Behavior Parameters setup, implement Agent callbacks, configure a trainer, collect training runs, inspect results, then test the exported policy in the actual environment.

Agent skeleton · API shape varies by package version
public override void CollectObservations(VectorSensor sensor)
{
    sensor.AddObservation(targetDirection);
}

public override void OnActionReceived(ActionBuffers actions)
{
    ApplyMove(actions.ContinuousActions);
}

public override void OnEpisodeBegin()
{
    ResetEnvironment();
}

Common failure modes

Reward hacking, observations with inconsistent scaling, overly complex actions, nondeterministic resets, and training distributions that differ from deployment. Track metrics and evaluate on scenarios the agent did not train on.

Interactive toy model · not an ML trainer

07

Multiplayer & networking

Networking adds latency, authority, synchronization, security, and failure modes. Decide your architecture before choosing a package.

Client-server fundamentals

A client-server model gives a server authority over important game state; peers send intent and receive replicated state. A server-authoritative design reduces cheating opportunities, but needs prediction/reconciliation for responsive controls.

State sync vs messages

Replicate state that other players need; send events/messages for one-time actions. Choose update rates and compression according to gameplay. Interpolate remote entities; don't blindly send every Transform every frame.

Unity networking choices

Netcode for GameObjects suits GameObject-oriented workflows; Netcode for Entities targets data-oriented architectures. Relay/Lobby or a dedicated server may support different hosting models. Verify current package compatibility, service terms, and platform requirements when you select your stack.

Latency, prediction & security

Clients can predict local movement, then reconcile against server truth. Interpolation smooths remote updates. Validate client commands on the server: never trust a client-provided score, damage value, or ownership claim.

Interactive network sketch

Why latency makes prediction matter

Adjust round-trip time. A plain request/response waits roughly one RTT before the server answer comes back; client prediction shows an immediate local response and reconciles later.

Debug, test & ship

A script is only done when it behaves in the target build and survives the project workflow.

Debugging habits

  • Read the first Console error and its stack trace.
  • Use breakpoints and inspect values; avoid relying only on log spam.
  • Reproduce with a small scene and known inputs.
  • Check object references, execution order, and active/enabled state.

Test layers

Unit-test deterministic game rules without scenes where possible. Use Unity Test Framework Edit Mode tests for pure/editor logic and Play Mode tests for engine behavior. Add build/device checks for platform-specific features.

Version control & build

Use text serialization and visible meta files for collaboration; choose Git LFS for large binary assets where appropriate. Commit project settings intentionally, pin package versions, and make builds reproducible.

Next project ladder
